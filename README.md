# whbus · 武汉公交实时通勤助手

一个为**日常通勤**设计的武汉公交安卓 App。不是"公交查询工具"的又一个复刻，而是回答三个具体问题：

1. **我现在出门，几点能到家？**
2. **最晚几点必须出发，才不会迟到？**
3. **坐哪几趟车、在哪换乘，路上花的时间最少？**

> 数据来自第三方非官方接口 `customized.wuhanbus.com/gps-resapi`，仅供个人通勤参考。
> 车辆位置可能有延迟，请以实际到站情况为准。

---

## 技术栈

| 层 | 选择 | 理由 |
|---|---|---|
| 框架 | Tauri v2 | 一个 APK 里同时有 Rust 后端和 WebView 前端 |
| 前端 | React 19 + TypeScript + Vite | — |
| 样式 | 手写 CSS + 设计令牌 | 不用 Tailwind，避免 v4 在安卓 WebView 的兼容风险，包体也更小 |
| 状态 | Zustand + localStorage | 只有收藏与地点需要持久化，localStorage 零依赖、同步读取，首屏不闪 |
| 图标 | 手写内联 SVG | 只用到十来个图标，引整套图标库不划算 |
| 后端 | Rust（Tauri commands） | 见下方「为什么所有网络请求都在 Rust 侧」 |

## 三个决定架构的实测结论

这三条都是对上游接口实测得出的，**与官方文档不符**，直接决定了本项目的设计。

### 1. 坐标转换不是"优化"，是"正确性前提"

- 安卓系统定位返回 **WGS-84**
- 公交接口使用 **GCJ-02**
- 两者在武汉的偏移实测 **约 587 米**（`src-tauri/src/gcj.rs` 的 `wuhan_offset_exceeds_nearby_radius` 测试守护此结论）
- 而 `/bus/nearBy` 的搜索半径**只有约 400 米**

**偏移量 > 搜索半径**，意味着不做转换会查到**完全错误的站点**，而不是"稍微不准"。

因此：**App 内部全程使用 GCJ-02**，只在边界转换。

### 2. `nscs` / `nsns`（剩余站数）字段完全不可用

文档声称这两个字段给出"到站剩余站数"。实测：**恒为哨兵值**（`-3`、`-2`）。

验证方式：找一条**确实有在线车辆**的线路（`420100-夜行518-1`），把它全部 20 个站点逐一查询，`nscs` 非负取值出现次数为 **0**。

因此"还有几站 / 还有几分钟"全部由本项目基于车辆坐标 + 站点表自行推算（`src-tauri/src/transit.rs`）。

### 3. 上游**没有任何班次计划表**

`/bus/detailData` 的 `plans` 字段实测恒为空数组，`/bus/search` 也不返回班次时刻。

这带来一个直接后果：**"最晚几点出发"无法从时刻表推导，只能靠自建的历史行驶时间模型**（`SpeedModel`）。

因此本 App 的 ETA 用**区间**而非单值表达——没有时刻表时预测本质是概率，
给一个假装精确的"7 分钟"是误导。区间宽度本身就在传达数据可信度，
而且**用得越久区间越窄**。

## 与上游文档不符的其他发现（以实测为准）

| 项 | 文档说法 | 实测 |
|---|---|---|
| `/bus/nearBy` 的 `distance` | 单位 km（`0.2009` ≈ 200m） | **单位是米，已放大 1000 倍**（`259.6372` = 259m）。本项目一律丢弃该字段，用 haversine 本地重算 |
| `/bus/search` 的 `stopDetailList` | 恒为空数组 | 传**站名**时有数据（传线路号时为空）。本项目据此实现站名搜索 |
| `/bus/search` 匹配范围 | 未说明 | **只匹配站名子串**，不认地址/小区名/写字楼名（`常青花园` ✅ / `楚天雅苑` ❌） |
| 请求时段 | 未说明 | **收班后接口整体返回空**（凌晨连 `715` 都搜不到）。这是服务端时段行为，非故障 |
| `nearBy` 半径 | 未说明 | 约 **400 米**，固定返回 **5 个站**，且同一物理站的东/西行会各返回一条 |
| 参数名 | — | 四个接口参数名各不相同：`lineCode` / `lineId` / `destinationId` / `longitude`+`latitude` |

## 为什么所有网络请求都在 Rust 侧

1. **密钥隔离**：加密接口的 `data` 是 SM4-ECB 密文，密钥由 `/sec/list` 的 `content` 与固定盐值拼成、**每日轮换**。放在 Rust 侧意味着密钥永不进入 WebView。
2. **无 CORS**：第三方接口不带 CORS 头，WebView 直连必然被同源策略拦下。
3. **统一限流**：上游建议请求间隔 ≥ 10 秒。限流器集中在 `Api::throttle` 一处才不会失控。
4. **请求预算**：一次朴素的换乘规划穷举可能打出 40+ 个请求。站点表（`/bus/line`）几乎不变，必须长期缓存（`AppState::line_cache`）。

前端只通过 `invoke` 拿干净的 JSON。

## 设计系统要点

完整令牌见 `src/styles/tokens.css`。

- **圆角比常规小一档**：卡片 18px（超过 24px 会立刻显得软糯，与"效率感"相悖）
- **分层主要靠 1px 描边**，阴影只留给浮在内容之上的元素
- **毛玻璃严格限定 3 处**：底部导航 / 决策卡 / 吸顶头部，并有 `@supports` 降级
- **线路色只作辅助**：上游不提供品牌色，且黄色线路配白字不可读。统一规则是"左侧 3px 色条 + 中性色文字"
- **不用 emoji 作结构图标**
- 深色与浅色主题的对比度**独立验证**，不互相推断

### 数据可信度的可视化（虚实线）

用户明确要求推测位置与真实位置可区分。映射集中定义在 tokens 里：

| 状态 | 线型 | 透明度 | 颜色 |
|---|---|---|---|
| 真实 GPS（< 3 分钟） | 实线 | 100% | 品牌蓝 |
| 数据偏旧（3-10 分钟） | 实线 | 72% | 警示黄 |
| **历史推测** | **虚线** | **55%** | 灰蓝 + "推测"角标 |
| 不可用 | 点线 | 35% | 灰 |

关键是**不只靠颜色区分**——已过站实心、未来站空心、当前位置实心+脉冲，三者在灰度下依然可辨。

## 本地开发

**本地只需要 Node 和 Rust**，安卓工具链交给 CI。

```bash
pnpm install
pnpm typecheck          # 前端类型检查
pnpm build              # 前端构建
cd src-tauri && cargo test --lib   # Rust 单测
```

### 在浏览器里开发 UI

```bash
pnpm dev   # http://localhost:1420
```

桌面环境下 `tauri-plugin-geolocation` 是 **mobile-only**：它不会报错，而是**静默返回 `0,0`**。
`src/lib/location.ts` 会自动识别这种情况并切到模拟位置（武汉常青花园片区），
同时把 `simulated` 标记透出到 UI，避免你对着几内亚湾的坐标调试武汉公交。

### 出安卓 APK

推送到 `main` 或手动触发 workflow 即可，无需本地配置任何安卓环境：

```
GitHub → Actions → Android APK → 下载 whbus-android-debug-arm64
```

debug APK 由 AGP 自动用 runner 上的 debug.keystore 签名，**不需要任何 secret**，可直接侧载。

> ⚠️ 每次 CI 构建的 debug keystore 都是新生成的，所以**连续两次构建的 APK 无法互相覆盖安装**，需要先卸载。

```
src/
  components/        通用 UI 原语 + 签名视觉（MiniTimeline 虚实线时间轴）
  screens/           四个 Tab：首页 / 规划 / 线路 / 我的

    api.ts           invoke 薄封装（前端不发任何网络请求）
    location.ts      定位 + WGS84→GCJ02（关键一步）
    polling.ts       自适应轮询（30/60/120s，后台暂停）
    store.ts         收藏、地点、情景判断
  styles/tokens.css  设计令牌（深浅双主题）

  gcj.rs             WGS-84 ⇄ GCJ-02 转换与路径几何
  sm4crypto.rs       SM4-ECB + PKCS#7 解密
  api.rs             公交接口客户端（限流、重试、密钥缓存）
  transit.rs         车辆定位、ETA 区间、速度模型

  commands.rs        Tauri 命令层
```

## 高德 Key 的配置

本项目需要**你自己**申请一个高德 Key 才能按地址搜索地点。原因见下。

### 为什么不能内置

1. 本仓库是**公开**的，硬编码的 Key 会被爬虫抓走、配额被刷爆
2. 别人 clone 这个项目时应该用自己的配额
3. 即使塞进 APK 也谈不上安全，但至少不该主动公开

### 怎么配

1. 到 [高德开放平台](https://lbs.amap.com/) 申请 Key，应用类型选 **「Web 服务」**
   （**不是**「Android 平台」——那个是给原生 SDK 用的）
2. 打开 App →「我的」→「高德地图」→ 粘贴 Key → 保存

Key 存在应用私有目录（安卓上其他应用无法读取，Unix 下 `chmod 600`），
只在 Rust 侧使用，**不会进入 WebView**。

### 不配 Key 会怎样

按地址搜索不可用，其余功能（实时公交、线路、规划）全部正常。
可以用「用当前位置」站在家或公司门口保存地点作为替代。

## 已知限制（都是上游接口的客观约束，不是实现偷懒）

1. **收班后搜不到任何站点**。上游 `/bus/search` 在夜间整体返回空，
   属服务端时段行为。App 会识别并提示"现在可能已收班"。
2. **没有班次计划表**。所以当一条线路的在线车辆都已驶过你的站时，
   规划会诚实地说"暂时给不出方案"，而不是猜一个候车时间让你误车。
3. **周边站点半径只有约 400 米**。家门到站超过这个距离时，
   算法看不到那个站。这是 `nearBy` 的硬限制。
4. **首次规划较慢**。上游要求请求间隔 ≥10 秒，而规划需要逐条拉取站点表。
   站点表长期缓存，第二次规划几乎是瞬时的。
5. **上游偶发超时**。客户端已内置重试与限流，但仍可能出现单次失败。
